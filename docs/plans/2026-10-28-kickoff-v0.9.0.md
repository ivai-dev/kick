# Kickoff 0.9.0 "Clarity, not ceremony": implementation spec

- **Repository:** the plugin repository. Branch `feat/kickoff-0.9.0` (cut from `feat/kickoff-0.8.1` after the 0.8.1 commit). **From:** 0.8.0 (0.8.1 is committed first and tagged, see §3). **To:** 0.9.0.
- **Problem:** a vague requirement should become, step by step, a decided solution, architecture, feature set and design, then a task breakdown and an effort estimate. Kickoff 0.8 is a delivery-governance pipeline (phase, gate, verify, commit, evidence), not a clarity engine:
  1. **Management set-up comes first.** `init` asks for roles with focus, a holiday calendar for every year, hard dates and releases before the product is understood.
  2. **Estimates are weak and scheduling dominates.** One person-day number per package, no range, no confidence, no basis; no estimate before a full WBS exists; the scheduler, calendar, workbook and slip procedure are most of `plan`; management work is modelled as level-of-effort packages.
  3. **Architecture is locked out entirely.** The hook blocks every file under `04-architecture/` before C3 and C4 and `solution` forbids even a draft, so the estimate after C2 is made with no technical picture, and feasibility surfaces only after the prototype.
  4. **Nothing shows what is still unclear.** `kickoff status` shows phases and gates. Uncertainty is spread over `open-questions.md`, `validation-plan.md`, *Proposed* ADRs and `plan.yaml` assumptions.
  5. **Ceremony in the early phases.** Every question needs a needed-by date although no calendar exists yet; every gate needs an evidence link even when the lead approves in the session.
- **Lead decisions (2026-10-28):** do all of: (A) a clarity register, (B) draft architecture at any time, (C) estimate separate from schedule, with ranges and confidence, (D) a slim `init`, (E) optional needed-by dates, (F) lighter gates. Then release and clean the local and remote repository.
- **Principle:** commit late, explore early. Features are locked with the customer before architecture is *committed* (C3, C4, ADRs *Accepted*); architecture can be *explored* as labelled drafts from the first week, and every estimate says how sure it is.

## 0. Rulings

| ID | Decision | Reason |
| --- | --- | --- |
| D-1 | **Clarity register `.kickoff/clarity.yaml`** (new, optional file). `areas` is a list of `{id, status, confidence, note, refs, updated}`. Ids: `problem, users, scope, solution, architecture, design, estimate` (a project may add more, pattern `[a-z][a-z0-9-]*`). `status`: `open, assumed, decided, validated`. `confidence`: `low, medium, high`. `refs`: IDs (`Q3`, `D2`, `A4`, `V1`, `ADR-002`). A missing file means "not started": nothing breaks. | The one place that answers "what is still unclear". |
| D-2 | **CLI:** `kickoff clarity` (table, the weakest area, its refs), `kickoff clarity init`, `kickoff clarity set AREA --status S --confidence C [--note T] [--ref ID]...`. The weakest area is the lowest `status` rank, then the lowest `confidence`, then pipeline order. `kickoff status` and the session-start hook append the clarity table when the file exists. The `estimate` line shows the spread `(max - min) / likely` of `kickoff estimate`. Phase skills end by setting the areas they touch (discovery: problem, users, scope; research: solution, architecture; ux-design and design-concept: design; plan: estimate). The router reports clarity before phases. | D-1. Phases keep deciding what *may* start; clarity decides what to work on *next*. |
| D-3 | **Estimate ranges.** `plan.schema.json` packages gain optional `min`, `max`, `confidence` (`low, medium, high`), `basis` (text). `effort` stays the likely value, so every old plan reads unchanged. `kickoff validate`: error unless `min <= effort <= max`. A package without `min`/`max` counts as `min = max = effort` and is reported as a point estimate. | Ranges and confidence without breaking any plan. |
| D-4 | **Feature-level estimate.** `features.schema.json` features gain optional `estimate: {min, likely, max, confidence, basis}` (person-days; `min` and `max` default to `likely`). A feature with packages in `wbs` is estimated from them; a feature without uses its own `estimate`. The warning "active feature without a WBS package" is raised only when the feature has neither. | A top-down estimate right after C2, before any WBS. |
| D-5 | **`kickoff estimate [--json FILE]`** (new): totals `min / likely / max` by release and by role (roles from packages only), the management overhead, the share of low-confidence items, and the basis line ("14 features top-down, 52 packages bottom-up, 9 low confidence"). `kickoff docs` writes `<docs_root>/06-planning/estimate.md` from it (generated block, `--check` covers it). `kickoff export` adds `effort_min`, `effort_max`, `confidence` as the last columns and fields. | Estimate becomes a first-class output, early and refined by phase. |
| D-6 | **Management overhead is a rate:** `project.yaml` `estimate: {overhead: 0.10}` (share of the work total, default `0.10` in the template, `0` when the block is absent). `kickoff:plan` stops adding level-of-effort management packages for plain project management; `effort_rate` packages stay supported for old plans. | Management is not a WBS line to schedule. |
| D-7 | **Scheduling is optional.** `project.yaml` `scheduling: on \| off`. An absent key means `on`, so existing projects behave as before; the new-project template writes `off`. With `off`: `kickoff schedule` and `kickoff workbook` print `scheduling is off (project.yaml scheduling: off)` and exit 0; `kickoff validate` does not need hard dates or gates in `plan.yaml`; `kickoff:plan` skips its schedule, workbook and slip steps. Turning it on is one edit of `project.yaml` after the lead confirms team, calendar and hard dates (the interview moves into `kickoff:plan`). | Schedule is a later concern; the estimate is the goal. |
| D-8 | **Slim `init`:** name, languages, one line on the idea (written into the vision seed in `AGENTS.md`), releases (default `[MVP, R2]`, confirm), security rules and forbidden phrases (each may be skipped). Roles, focus, calendar, holidays and hard dates are asked by `kickoff:plan` when the lead turns scheduling on. The template keeps default roles so `project.yaml` stays schema-valid. | Decision D. |
| D-9 | **Draft architecture.** The pre-write hook lets a Write or Edit under `04-architecture/` through when the resulting file has a `Status: Draft` line in its first 20 lines; otherwise the old rule applies (blocked until C3 and C4). `kickoff validate` adds an error: an ADR with status *Accepted* while `kickoff can solution` is blocked. `kickoff:research` gains a step "Architecture sketch (draft)": `system-architecture.md` and `data-model.md` from the templates, `Status: Draft (hypothesis)`, written to test feasibility and to feed the estimate (set clarity `architecture` to `assumed`). `kickoff:solution` starts from the draft and turns it into the accepted documents; its "never a draft" sentence is replaced by the rule that a draft binds nothing and no implementation starts from it. | Feasibility early; nothing is committed before the customer signs off. This changes the core principle text: README, `using-kickoff`, `solution`, `lessons.md` are edited to say *commit* late, not *explore* late. |
| D-10 | **Lighter gates.** `--evidence` becomes optional for C1, C2, C5 and C6 (approved by the project lead): when omitted it records `decision in session <date>`. It stays required for CD, C3 and C4 (the customer). Skills no longer require a separate `chore: approve` commit; the `state.yaml` change goes in the next commit. | The evidence rule protects customer decisions; the lead's own approvals do not need a link. **Strike this row to keep the old rule.** |
| D-11 | **Needed-by dates are optional** while scheduling is off: `open-questions.md` keeps Blocks and Owner and gains a Priority (`now, soon, later`); `Needed by` is required only when scheduling is on. Template, `discovery` and Verify text change; no CLI check reads these tables. | The date has no calendar to mean anything yet. |
| D-12 | **`kickoff status` names every phase in progress** (`continue kickoff:research and kickoff:feature-map`), not only the first. Reopening a gate keeps marking all later phases stale: the phase chain is linear, so a dependency graph would stale the same set. | Honest about what changes: runs side by side already work. |
| D-13 | **Not in this release:** ECC stays required (`kickoff ecc doctor` still stops a session); the post-write hook still reports validate errors after a yaml edit; no change to `design-concept`, `prototype`, `signoff` or `feedback` beyond clarity touchpoints. | Out of scope for this release. |
| D-14 | **Version 0.9.0**, not breaking for data: no schema field is removed or made stricter for old files, except the new ADR check (D-9). State migration is unchanged. The CHANGELOG lists the hook change (D-9) and the optional-evidence change (D-10) under Changed. | Old projects keep working. |
