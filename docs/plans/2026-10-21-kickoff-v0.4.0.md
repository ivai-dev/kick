# Kickoff 0.4.0 "ECC bridge": implementation spec

- **Repository:** the plugin repository (skills `skills/`, agents `agents/` (new), hooks `hooks/hooks.json`, CLI
  `cli/src/kickoff/`, tests `cli/tests/`). Branch `feat/kickoff-0.4.0`. Merges, pushes and tags are confirmed with
  the project lead first (AGENTS.md).
- **From:** 0.3.1. **To:** 0.4.0. **ECC tested:** 2.2.3 (`ecc@ecc`, commit `ef648e0`).
- **Lead decisions (2026-10-21), the frame of this spec:**
  1. ECC is a **required** dependency. Skills have no fallback branch for a missing ECC.
  2. Kickoff **stops at tickets and hands off to ECC** for build, QA and release. Kickoff gets no build phases.
  3. Releases go **in order**:
     - 0.4.0, this ECC bridge (the prototype kit stays as it is);
     - 0.5.0, the FE foundation (a real frontend project replaces the HTML kit);
     - 0.6.0, the handoff (ticket specs that ECC `orch-*` runs, and a tickets pull that reads PR and CI state).
  4. Where an ECC handoff is broken, **kickoff patches around it** and does not wait for upstream.
- **Source:** the 2026-10-21 architecture review of kickoff 0.3.1 and the map of ECC 2.2.3, summarised in §1.
- **Audience:** an engineer agent with no other context. Each task in §12 ends with a command and its expected output.

## 1. Why: review summary

**Kickoff 0.3.1:**
- It is strong where ECC has nothing: gates in code (`state.py:20-98`), IDs that never change, estimate, schedule, workbook, ticket sync, and lessons traced to checks.
- It rebuilds what ECC already has:
  - Build plan and Task run duplicate the planner and orch-pipeline;
  - the design-review loop is a hand-written multi-agent pass;
  - `proto check` duplicates browser QA;
  - rulings and lessons duplicate session learning.
- There is no `agents/` folder, and the only hook is SessionStart.
- `cli/tests/test_skills.py:30` forbids naming any non-`kickoff:` skill, so integration is impossible today.

**ECC 2.2.3:**
- It covers research, decisions, review agents, TDD, build, QA, PRs and learning.
- It has no estimate or schedule tooling, no customer gate, and no epic or release management.
- Friction points:
  - GateGuard asks for facts before the first write of every file and before the first Bash command;
  - the router does not know kickoff;
  - two handoffs are broken (`plan-orchestrate` emits the unloaded `/ecc:orchestrate`, and `epic-*` uses a relative script path);
  - the ADR skill writes `docs/adr/`.

## 2. The ECC contract: `skills/using-kickoff/references/ecc.md`

Every skill that uses ECC points here and names the component in its own step. The file holds:

1. **The ownership rule** (E-1) and the list of ECC writers that are not used for kickoff artefacts (E-2).
2. **How to call ECC:**
   - skills with the Skill tool (`ecc:<name>`);
   - agents with the Agent tool (`subagent_type: "ecc:<name>"`);
   - ECC scripts only through `kickoff ecc run`;
   - ECC file paths, for example a skill an agent must read, only through `kickoff ecc root`.
3. **Gates do not merge.** ECC's own approvals (orch-pipeline plan approval and commit confirmation, ADR confirmation) never count as kickoff gate approvals. Kickoff gates still need `kickoff gate approve --by --evidence`.
4. **GateGuard:** answer its facts when it asks. `kickoff ecc setup` exempts kickoff documents (E-8). Never set `ECC_GATEGUARD=off` on the lead's behalf.
5. **ecc-router:** inside a repository with `.kickoff/`, `kickoff status` decides the next step; a router hint never overrides it.
6. **The delegation table**, the same rows as §6 below: phase, step, ECC component, input given, what comes back, where kickoff writes it.
7. **Patched handoffs** (E-10).

## 3. CLI

### 3.1 `kickoff/ecc.py`

```python
TESTED_ECC = "2.2.3"
MIN_ECC = "2.2.3"
COMPONENTS = {  # kind -> names; the only ECC names skills, agents and references may use
    "skill": ["search-first", "deep-research", "council", "product-lens", "accessibility", "frontend-a11y"],
    "agent": ["architect", "planner", "security-reviewer", "database-reviewer"],
    "script": ["scripts/github-coordination.js"],
}
ROUTER_BEGIN, ROUTER_END = "<!-- kickoff:router:begin -->", "<!-- kickoff:router:end -->"
```

Paths: skill `skills/<name>/SKILL.md`, agent `agents/<name>.md`, script `<path>`, all under the ECC root.
`installed_plugins.json` is read from `$CLAUDE_CONFIG_DIR/plugins/` when that variable is set, otherwise from
`~/.claude/plugins/`. Entry key: `ecc@ecc`. Entry fields used: `scope`, `projectPath`, `installPath`, `version`.

### 3.2 `kickoff ecc root`

Prints the ECC root (E-3) and exits 0. Exit 1 with `error: ECC is not installed (no ecc@ecc in installed_plugins.json)`
when no entry is found or its `installPath` does not exist.

### 3.3 `kickoff ecc doctor`

Prints one line per check, then `ecc doctor passed` or `ecc doctor failed`. It works with or without `.kickoff/`; checks
D5 and D6 run only inside a project.

| Check | Fails (exit 1) | Warns (`warn:`) |
| --- | --- | --- |
| D1 installed | no root (§3.2) | — |
| D2 version | below `MIN_ECC` | major or minor above `TESTED_ECC` |
| D3 components | any `COMPONENTS` path missing | — |
| D4 hooks profile | — | `ECC_HOOK_PROFILE` or `ECC_DISABLED_HOOKS` disables `session:start` (kickoff then sees no instincts; informational) |
| D5 GateGuard exemption | — | the project `.claude/settings.json` `env.GATEGUARD_EXEMPT_GLOBS` lacks `.kickoff/**` or `<docs_root>/**` (fix: `kickoff ecc setup`) |
| D6 router | — | `~/.claude/skills/ecc-router/references/routing-table.md` exists without the kickoff block (fix: `kickoff ecc setup --router`) |

### 3.4 `kickoff ecc setup [--router] [--dry]`

Run inside a project only (exit 2 without `.kickoff/`).

- **Settings:** reads `.claude/settings.json` (creates `{}` when missing) and adds the three globs of E-8 to `env.GATEGUARD_EXEMPT_GLOBS` (comma-separated), keeping existing entries and every other key. It is idempotent. JSON is written with 2-space indent and a trailing newline. A file that is not valid JSON stops the command with exit 2, and nothing is written.
- **`--router`:** appends this block once, at the top of the "## 3. Planning lane" section of the router table (or at the end of the file when that heading is missing):

```markdown
<!-- kickoff:router:begin -->
| Repository has `.kickoff/` and the request is kickoff work (discovery, scope, features, UX, prototype, sign-off, architecture, plan, estimate, tickets) | kickoff:using-kickoff | — |

Inside a repository with `.kickoff/`, kickoff phases own the PRD, ADR, architecture, plan and ticket artefacts: do not route them to plan-prd, blueprint, architecture-decision-records or epic-decompose. Code work on tickets routes to the orch-* owners as usual.
<!-- kickoff:router:end -->
```

- **`--dry`:** prints a unified diff of each file it would change and writes nothing.

### 3.5 `kickoff ecc run <script> [args…]`

`<script>` is a `COMPONENTS["script"]` entry without `scripts/` and `.js` (for example `github-coordination`). It runs
`node <root>/scripts/<script>.js args…` with the project root as the current directory, passes stdout and stderr through,
and returns node's exit code. An unknown script gives exit 2; a missing `node` gives exit 2 with `error: node not found`.

### 3.6 `kickoff hook <event>`

Each event reads the hook JSON from stdin. In a directory tree without `.kickoff/` it exits 0 at once. An internal error
gives exit 1 with one stderr line. This is non-blocking, so a kickoff bug never blocks the user, but it stays visible.

- **`session-start`:** prints `kickoff project detected: use the kickoff:using-kickoff skill.`, then the output of `kickoff status`, then the `warn:` and failure lines of doctor checks D1–D3 only (fast, no router read). It always exits 0.
- **`pre-write`:** the input is `tool_input.file_path` for Write, Edit and MultiEdit. It blocks with exit 2 and one stderr reason when the resolved path is:
  - `.kickoff/state.yaml`: `state.yaml is written by the kickoff CLI only: use kickoff phase, kickoff gate or kickoff proto record`;
  - `.kickoff/tickets.yaml`: `tickets.yaml is written by kickoff tickets only`;
  - under `<docs_root>/04-architecture/` and not under `adr/`, while `blockers(state, "solution")` is non-empty: `architecture documents wait for C3 and C4: <blocker lines>`;
  - a kit core file under `proto.dir` (`narrow.html`, `test/**`, `js/{route,logic,core,ui,ui-form,ui-data,charts,scope,shell,scenario,audit,main}.js`): `the kit core is replaced by kickoff proto update; extend the kit in project files`.
  
  Everything else exits 0.
- **`post-write`:** when the path is `.kickoff/*.yaml` (other than `state.yaml` and `tickets.yaml`), it runs the same check as `kickoff validate`. Errors give exit 2 with the error lines on stderr, so the model sees them right after its edit. Warnings and a clean result exit 0 and print nothing.

### 3.7 `kickoff proto record --artifact <link-or-path> [--version <n>]`

Writes `state.yaml` `prototype: {artifact, version}`. Without `--version` it uses the recorded version + 1 (1 when there is none). An explicit version lower than the recorded one gives exit 2. It prints `prototype v<n>: <artifact>`.

### 3.8 `kickoff check-docs <paths…>`

For each file, and each file under a folder argument, with a text extension (`.md`, `.yaml`, `.js`, `.html`), it reports:
- `<path>:<line>: placeholder {{…}}` for each `{{` that is not inside a fenced code block;
- `<path>:<line>: forbidden phrase /<pattern>/` for each match of `rules.forbidden_phrases` in `project.yaml`.

It exits 1 when there are any findings and 0 otherwise, printing `check-docs passed (<n> files)`.

## 4. Hooks: `hooks/hooks.json`

```json
{
  "hooks": {
    "SessionStart": [{ "matcher": "startup|resume|clear", "hooks": [{ "type": "command", "timeout": 15,
      "command": "if command -v kickoff >/dev/null 2>&1; then kickoff hook session-start; elif [ -d .kickoff ]; then echo 'kickoff CLI missing: see kickoff:using-kickoff.'; fi" }] }],
    "PreToolUse": [{ "matcher": "Write|Edit|MultiEdit", "hooks": [{ "type": "command", "timeout": 10,
      "command": "if command -v kickoff >/dev/null 2>&1; then kickoff hook pre-write; fi" }] }],
    "PostToolUse": [{ "matcher": "Write|Edit|MultiEdit", "hooks": [{ "type": "command", "timeout": 20,
      "command": "if command -v kickoff >/dev/null 2>&1; then kickoff hook post-write; fi" }] }]
  }
}
```

ECC's hooks run alongside these. Order between plugins is not guaranteed, and nothing here depends on it.

## 5. Agents (`agents/`, plugin agents `kickoff:<name>`)

Frontmatter: `name`, `description` ("Use when …"), `tools: Read, Grep, Glob, WebSearch, WebFetch`, `model: inherit`.
The body states the output contract of `skills/prototype/references/design-review.md` §3–5, unchanged:

| Agent | Role | Returns |
| --- | --- | --- |
| `viewpoint-reviewer` | One audience or role group, named in the prompt, with its journeys, home, navigation and wording | research with sources, top ten changes, findings per screen (Screen, Element, Problem, Why for this role, Change, Rank P1–P3), look-alikes, decisions to revisit |
| `craft-auditor` | Wording, numbers, type, spacing, colour, accessibility. Reads `content-and-craft.md` and the ECC skills `accessibility` and `frontend-a11y` by the paths `kickoff ecc root` gives | same table |
| `ia-reviewer` | Navigation per role, naming, home shapes, guidance devices, motion | same table |
| `integrator` | Reads the reports and cross-reviews named in the prompt | the `upgrade-v<n>.md` plan of §5 of the review loop |

The calling skill writes each returned report to `<folder>/r<n>-<viewpoint>.md`, `x-r<n>.md` or `upgrade-v<n>.md`. The
cross-review round runs the same agents again, each given the other reports.
