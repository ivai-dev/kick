# kick v1.0.0 — brainstorm

- **Status:** Decided (section 13); the implementation plan is `2026-10-28-kick-v1.0.0.md`
- **Date:** 2026-10-28
- **Builds on:** 0.9.0 "Clarity, not ceremony" (`2026-10-28-kickoff-v0.9.0.md`)

## 1. The change in one paragraph

kickoff 0.9 is still a bid-delivery pipeline: 10 phases in a fixed order, 7 gates (C1, C2, CD, C3, C4, C5, C6), numbered items (A1, Q3, D2, F1.2, ADR-001, WBS 1.1.1) in documents and in conversation. A survey of the repo counts 393 gate codes, 221 "gate", 131 "ADR", 51 "baseline" and 46 "WBS" in the skills and README alone. The person working with the AI does not know this vocabulary and cannot tell what they are agreeing to. The clickable prototype phase cost a lot and was thrown away, because feedback on a whole new product changes a lot.

**kick** is a starter for any piece of work done with AI. It gives a short standard flow, templates and rules for working with ECC, in plain words. There are two kinds of kick:

- **A product kick** takes a vague idea to a product the person can see and use. Its end is reached when four things exist:
  - the real frontend code, running on a mock API with realistic sample data;
  - the decisions, written down;
  - a draft API contract and a draft data model;
  - the list of feature kicks that come next.
- **A feature kick** takes one feature, module or app in a running project from understanding to working code.

Everything that belongs to bidding for a project is dropped: customer demo ceremony, sign-off records, evidence links, calendars and dates, the estimate workbook and the tracker export.

## 2. What stays (the parts that earned their place)

- **Settle what is expensive to change early, with the person, in plain words.** Solution, architecture, technology and UI direction are chosen from options that differ in kind.
- **Plain words:** every question to the person says what is being decided, what each answer means and costs, and what becomes expensive to change. It is now the core rule, not a patch.
- **Estimates as ranges:** min / likely / max with a confidence and a basis, narrowing at each milestone.
- **What is still unclear** is visible, now as `[unclear: …]` markers in the text.
- **ECC does the work**; kick owns the flow, the templates and the documents.
- **The design philosophy** (the brief decides the form, no catalogue defaults, the fit test) and the five design review agents.

## 3. The two kinds of kick

### Product kick: from a vague idea to a product you can see

```
Understand → Shape → Plan the UI → Build the real UI on a mock API → People try it, fix
→ agreed "this is the product" → END
```

| Step | What happens | Agreed with the person |
| --- | --- | --- |
| **Understand** | Interview one question at a time, play back. Problem, users, in / out, success, rough feature list, `[unclear: …]` markers. | "This is what I understood." |
| **Shape** | Solution and architecture (2–3 options that differ in kind), technology (frontend, backend, hosting; **not** the data model yet), screen map by journey with a cut line for the first release, UI direction (2–3 directions, **one key screen each**), design rules (colour, type, spacing, components, tone). Technical risks listed. Rough estimate for the whole product. | "This is how we'll build it and how it will look." |
| **Plan the UI** | Tasks for the UI stage with ranges; the technical probes; the criteria for "this is the product". | "These are the UI tasks, about X–Y days." |
| **Build the real UI** | Real frontend code in the chosen stack, with tests, calling one API layer that returns realistic mock data. Each mock endpoint records what it takes and returns, its empty, loading and error states, paging, and who may see what; it is the draft contract. Endpoints that would be expensive to build for real are tagged and priced. In parallel: small throw-away probes for the technical risks. The five design reviewers review the running UI journey by journey (screenshots). Then **real users try it with concrete tasks**. Every comment is classified (now / later / no, with the extra days); at most two rounds per screen. A "sample data" banner and the remaining estimate keep expectations honest. | "This is the product" (against the criteria set in the plan). |

**End of a product kick:**
- **The code stays:** the frontend and its mock layer.
- **The documents move:** the decisions, the draft contract and the draft data model go into the shared project documents (section 4).
- **The plan of what comes next:** the product kick leaves the list of feature kicks, in order, with dependencies, a range estimate each and the first-release cut.
- **The first feature kick is always "Foundation":** sign-in, database, deployment, and one flow running end to end for real. This proves the architecture.

A product without a UI (a service, an API, a tool) skips the UI stage. Its product kick ends at the agreed contract, a mock server or contract tests, the decisions and the feature list.

### Feature kick: one feature, module or app in a running project

```
Understand → Shape → Plan → Build → agreed "it works as agreed" → END
```

- **Shared documents:** the kick reads the project documents first and writes back what it changed.
- **Shape is light:** it reuses the existing look and rules, with options only where the feature has a real choice.
- **Build:** each task goes to the matching ECC pipeline (add, change, fix). On a product built by a product kick, the feature builds the real backend for its part and replaces its mock endpoints. Contract tests prove that the real API answers as the mock did, so the screens do not change.
- **Screens:** built straight in the real code, shown, adjusted, kept.
- **Small features:** understand and shape may be agreed in one question. A one-line fix needs no kick at all: kick sends it straight to ECC.

## 4. Shared project documents: "how it is now" and "this change"

```
docs/kick/
  project/            ← how the product is now; every kick reads it
    project.yaml      languages, overhead, time budget (optional)
    overview.md       problem, users, scope
    design.md         architecture, technology, UI direction and rules, screen map
    api.md            API contract (mock → real, endpoint by endpoint)
    data.md           data model (draft → real, feature by feature)
    roadmap.md        the feature kicks: order, dependencies, ranges, first-release cut
  <kick>/             ← one change: brief, design, tasks, feedback, log
  done/<kick>/
```

- **A new product:** its product kick creates `project/`.
- **A running project:** `project/` is created once by reading the existing code.
- **When a kick finishes:** it writes its changes into `project/`. A kick that changes something other features use is warned first.

## 5. Weak points of this flow and what patches them

| Weak point | Patch |
| --- | --- |
| The riskiest work (business rules, integrations, data migration, performance, security) is invisible in a UI and would surface last | Technical probes run in parallel during the UI stage; the Foundation feature kick comes first |
| A mock API makes everything look free (complex search, live updates, heavy reports) | An architecture review of the mock contract before people try it; costly endpoints are tagged and priced; mocks have delay and errors |
| "It's almost done" illusion | A "sample data" banner; every showing states what remains (`kick estimate`) |
| Seeing the product invites new scope | Every comment is classified now / later / no with the extra days; the person weighs it |
| The frontend quietly defines the data model and holds server logic | Mocks return data only, no business logic; places where the UI does server work are marked; roles and permissions are in the mocks from the start; contract tests when the backend arrives |
| The architecture is unproven until the backend | Foundation is the first feature kick and runs one flow end to end |
| "This is the product" never arrives | Criteria agreed in the plan: main journeys complete, at most two rounds per screen, how many unclear points remain |
| Review cost and who gives feedback | Reviews per journey, not per screen; all five reviewers only for a product kick; real users (at least one) asked by name |
| Each feature designs its own tables and API | `project/data.md` and `api.md` are shared; each feature details its part; kick warns when a feature changes something another feature uses |

## 6. How professional teams do it, and what kick takes

| Practice | Source | Idea | In kick |
| --- | --- | --- | --- |
| Inception / discovery phase | Thoughtworks and agencies | Workshops → scope, journeys, wireframes, clickable prototype, architecture, estimate | The product kick, without the thrown-away prototype |
| Dual-track agile | Marty Cagan, Jeff Patton | Discovery and delivery side by side | Product kick (discover), feature kicks (deliver) |
| Walking skeleton / tracer bullet | Alistair Cockburn; *The Pragmatic Programmer* | A thin flow through every layer early | The Foundation feature kick |
| Executable architecture baseline | RUP elaboration | Architecture is settled when it runs, not on paper | Foundation, plus the probes |
| Spike | Extreme Programming | Time-boxed experiment, code thrown away | Technical probes |
| API-first + mocks; consumer-driven contracts | OpenAPI, Prism, MSW; Pact | Agree the contract, front end on mocks, back end to the contract, contract tests | Mock layer, `api.md`, contract tests in feature kicks |
| Design Sprint | Google Ventures | Prototype and test with 5 real users on concrete tasks | Real users try the real UI with tasks |
| Shape Up | Basecamp | Rough shaping before building; an *appetite* (time budget) instead of an estimate; vertical slices | Shape step; optional time budget that shapes the scope |
| Story mapping | Jeff Patton | Journeys left to right, detail top to bottom, a cut line per release | Screen map by journey with the first-release cut |
| Cone of uncertainty | Barry Boehm, Steve McConnell | Early estimates can be off by 4x and narrow at milestones | Ranges narrowing per milestone |
| Design system before screens | common practice | Tokens and components first | Design rules in shape |

What changes with AI: these practices were born when code cost more than drawings, so prototypes were drawn and thrown away. With AI, a real UI in code costs about as much as a detailed design file, and it is kept. Building the real UI on mocks is the professional practice, updated for that cost.

## 7. Languages

- **When:** asked once per project, at the first kick.
- **How:** as one proposal to confirm, never five questions. The proposal covers:
  - **chat:** the language the person writes in;
  - **documents:** the same as chat;
  - **code (names, comments):** English;
  - **UI text:** asked; more than one language means multi-language support from the start, which costs effort;
  - **commit messages:** English.
- **In a running project:** the proposal follows what the code already does (comments, UI strings, commit history).
- **Where it is kept:** stored in `project/project.yaml`. Repeated in one line at every session start, so every session follows it.
- **Side effects:** the UI language list is a decision in shape, with its cost. The mock data uses the UI language.

## 8. Companions: suggested when a step needs them, installed after a yes

1. **When:** at the start of a step, kick checks whether that step needs a tool the machine lacks.
2. **What it says:** one line on what the tool does for this step, whether it needs an account, and that it is optional.
3. **The choices:** install now, later, or don't ask again.
4. **After a yes:** kick installs it itself, reports the result and says when a restart is needed.
5. **Memory:** answers are remembered per user, and `kick companions` lists them and offers again.
6. **Limits:** kick never installs without a yes and never asks in the middle of a task.

| Step | When | Companion |
| --- | --- | --- |
| Understand | the idea is vague | superpowers (brainstorming only), mattpocock-skills (`grill-me`) |
| Shape, architecture | a diagram is needed | drawio |
| Shape, UI | always | frontend-design, impeccable, ui-ux-pro-max (if missing) |
| Shape, UI | the team designs in Figma | figma |
| Shape, UI | many variants quickly | superdesign (account) |
| Build UI | reviewers look at the running UI | a browser tool (Playwright MCP, or ECC's Chrome DevTools) |
| Build | current library docs | Context7 |
| Every step | ECC missing or too old | ECC: the one required companion; kick stops until it is installed |

superpowers brings its own plan and execute chain. kick uses only its brainstorming, and says so when it offers it.

## 11. Rename and the name

- **New names:** plugin, marketplace, CLI and skill prefix become `kick`; the repo becomes `ivai-dev/kick` (GitHub redirects the old URL; marketplace users re-add once).
- **To verify first:** no `kick` plugin in the official marketplace.

## 12. Earlier ideas, superseded

- The clickable sketch, `playground` as a companion, and a whole-product UI concept round: replaced by one key screen per direction and the real UI on mocks.
- "Build the backend inside the product kick": the product kick ends at the UI. The backend is built feature by feature.
- Companions offered once at the start: now offered at the step that needs them.

## 13. Decisions (2026-10-28)

1. **Files:** one folder per kick under `docs/kick/`, plus the shared `docs/kick/project/`.
2. **Strictness:** advice only. kick says what is not agreed and the risk, then asks. Nothing is blocked, and there is no pre-write blocking hook.
3. **Bid extras:** dropped. That covers the workshop, sign-off, evidence, schedule, calendar, dates, workbook and export.
4. **CLI:** a slim `kick` CLI.
5. **Companions:** suggested at the step that needs them and installed by kick after an explicit yes.
6. **No throw-away prototype.** UI direction is shown as one key screen per direction. The UI the person tries is the real frontend.
7. **Two kinds of kick:**
   - A product kick ends at the real UI on a mock API, the written decisions, the draft contract and data model, and the feature list.
   - Feature kicks follow, and Foundation comes first.
8. **The data model and the final API** are settled after the person has used the real UI, feature by feature. This is advice, not a block.
9. **The weak-point patches of section 5** are part of the flow.
10. **Practices adopted from section 6:**
    - an optional time budget;
    - a screen map by journey with a release cut;
    - tasks for real users;
    - contract tests;
    - throw-away probes.
11. **Languages** for chat, documents, code, UI and commits are confirmed once per project and repeated at each session start.
12. **The review agents** review the running UI per journey. All five run only for a product kick.
