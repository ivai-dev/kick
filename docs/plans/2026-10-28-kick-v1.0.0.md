# kick 1.0.0: implementation plan

- **Repository:** the plugin repository, branch `feat/kick-1.0.0` cut from `main` (`b5c380b`, v0.9.0). **From:** kickoff 0.9.0. **To:** kick 1.0.0 (breaking).
- **Decisions:** `2026-10-28-kick-v1.0.0-brainstorm.md`, section 13. In short:
  - **Rename:** kickoff becomes kick.
  - **Two kinds of kick:**
    - a **product kick**, from a vague idea to the real frontend on a mock API, plus the written decisions, the draft contract and data model, and the feature list;
    - **feature kicks** after it, Foundation first.
  - **Shared project documents:** `docs/kick/project/`.
  - **Wording:** plain words, with no gates or numbered items.
  - **Strictness:** advice only.
  - **Bid extras dropped.**
  - **Slim CLI.**
  - **Languages:** confirmed once per project.
  - **Companions:** suggested at the step that needs them and installed after a yes.
- **Principle:** settle what is expensive to change early, with the person, in plain words. The data model and the final API wait until the person has used the real UI. Estimates are ranges that narrow at each milestone. ECC does the work.

## 0. Rulings

| # | Ruling | Reason |
| --- | --- | --- |
| 1 | **Names.** Plugin and marketplace `kick`; skills `kick:<name>`; slash command `/kick`; CLI `kick`; Python package `kick` (`cli/src/kick/`), distribution `kick-cli`; repo `ivai-dev/kick`. The local folder keeps its name (renaming it would orphan this project's Claude memory). | Short verb: "kick a product", "kick a feature". |
| 2 | **Layout.** `docs/kick/project/` holds how the product is now: `project.yaml`, `overview.md`, `design.md`, `api.md`, `data.md`, `roadmap.md`. Each kick is `docs/kick/<slug>/`: `kick.yaml`, `brief.md`, `design.md`, `tasks.md`, `feedback.md`, `log.md`. Finished kicks move to `docs/kick/done/<slug>/`. Slug pattern `[a-z0-9][a-z0-9-]{1,40}`; `project` and `done` are reserved. | Brainstorm section 4. |
| 3 | **`project/project.yaml`** (schema v1): `languages: {chat, docs, code, ui: [..], commits}` (language tags such as `vi`, `en`); optional `overhead` (share, default 0); optional `budget_days` (time budget). | Languages confirmed once; the time budget is an optional input to shaping. |
| 4 | **`<kick>/kick.yaml`** (schema v1): `title`, `kind` (`product`, `feature`), `started` (date), `status` (`active`, `paused`, `done`), `agreed` (map from `understand`, `shape`, `plan`, `result` to a date; missing means not agreed yet), optional `budget_days`, optional `roadmap` (the roadmap key this feature kick implements). The current step is derived: the first of understand → shape → plan not agreed, else `build`; `result` agreed → ready to finish. `result` is "this is the product" for a product kick and "it works as agreed" for a feature kick. | One small machine file; everything else is prose. |
| 5 | **Unclear points** are `[unclear: …]` markers in any kick or project Markdown file. `kick status` counts and lists them. | One mechanism, no second register. |
| 6 | **Tables the CLI reads** (format below): `## Tasks` in `<kick>/tasks.md`, `## Features` in `project/roadmap.md`, `## Endpoints` in `project/api.md`. Everything else is prose for people. | Readable by the person, editable by the AI, checkable. |
| 7 | **Agreements replace gates.** At the end of understand, shape, plan and build the skill asks one plain question. On a yes it writes the date into `agreed` and a dated line into `log.md`, saying what was agreed in the person's words. A later change to an agreed file clears that step and later ones, and the log says why. For a small feature kick, understand and shape may be agreed in one question. | Plain words, no gate codes. |
| 8 | **Advice only.** There is no blocking hook and no refused command. The skill states what is missing and the risk, asks, and logs the answer, for example when building before shape is agreed, writing the data model before "this is the product", or planning over open unclear markers. `kick check` reports such cases as warnings, never errors. | Decision 2. |
| 9 | **Product kick build** (the UI stage), all in the skill's reference:<br>(a) real frontend in the chosen stack, with tests, behind one API client layer;<br>(b) mock endpoints return realistic data in the UI language and carry no business logic; each endpoint is a row in `project/api.md`, with roles, its empty, loading and error states, paging, `Status: mock`, and a `cost` note for endpoints that are expensive to build for real;<br>(c) an architecture review of the mock contract before people try it;<br>(d) throw-away technical probes for the risks listed in shape, whose results are recorded in `design.md` and whose code is deleted;<br>(e) the design reviewers on the running UI per journey;<br>(f) real users try the UI with concrete tasks;<br>(g) comments are classified in `feedback.md` as now, later or no, with extra days, at most two rounds per screen;<br>(h) a "sample data" banner, and the remaining estimate stated at every showing;<br>(i) the "this is the product" criteria are written in `tasks.md` at plan time. | Brainstorm sections 3 and 5. |
| 10 | **Finishing a product kick:** promote the decisions, the screen map, the draft contract and the draft data model into `project/`, and write `project/roadmap.md`. The roadmap's first row is always **Foundation**: sign-in, database, deployment, and one flow running end to end. Then `kick done`. A product without a UI skips the UI stage; its result is the agreed contract with a mock server or contract tests. | Brainstorm section 3. |
| 11 | **Feature kick build:** each task goes to an ECC pipeline (`orch-add-feature`, `orch-change-feature`, `orch-fix-defect`, `tdd-workflow`). A feature on a mock-backed product builds the real endpoints for its part, adds contract tests (the real endpoint answers as the mock did) and flips them to `Status: real` in `api.md`. It details its part of `data.md`, and kick warns when it changes something another feature uses. Screens are built in the real code, shown, adjusted. Finishing: write the changes into `project/`, link the roadmap row, then `kick done`. | Brainstorm section 3. |
| 12 | **A one-line fix or a small change needs no kick.** The router sends it to ECC directly. | The smallest process that is enough. |
| 13 | **Languages:** `start` proposes one set to confirm (chat = the person's language, docs = chat, code = English, UI = asked, commits = English; in a running repo it follows what the code does) and runs `kick init` with it. The session-start hook prints the line. Two or more UI languages are recorded as a decision in shape, with their cost. | Decision 11. |
| 14 | **Companions** come from a catalogue in `companions.py`, each entry: id, type (plugin or MCP server), install command, the step and condition that call for it, whether an account is needed, and a one-line purpose. At the start of a step the skill runs `kick companions --step <step>`, offers the missing ones in plain words (install now, later, don't ask again), installs after an explicit yes (`claude plugin install …` or `claude mcp add …`), reports the result and the restart need, and records the answer (`kick companions mark`). Answers live in `~/.kick/companions.yaml`; `KICK_HOME` overrides it. Plugins are detected from `installed_plugins.json` (code from `ecc.py`), MCP servers from the Claude config. Never install without a yes, never ask mid-task. ECC is the one required companion: `kick doctor` fails without it. | Decision 5. |
| 15 | **Review agents** (art-director, ia-reviewer, viewpoint-reviewer, craft-auditor, integrator) keep their roles; their wording loses gate, phase and ID words. They review screenshots and journey notes the skill saves under `<kick>/reviews/<date>/`, because the agents cannot drive a browser. All five run for a product kick; a feature kick with UI runs ia-reviewer and craft-auditor by default. | Decision 12. |
| 16 | **Removed:** phases, gates, state, `can`, `phase`, `gate`, `clarity`, `schedule`, `workbook`, `export`, `docs` generation, `prototype record`, the LibreOffice/docker check, the pre-write hook, `ecc run`, `ecc root`, the router-table patch, `features.yaml`, `plan.yaml`, `state.yaml`, the old `project.yaml`, the `signoff` skill, the customer templates, the clickable-prototype method, and numbered IDs everywhere. | Decisions 3, 4, 6. |
| 17 | **kickoff 0.9 projects** are not converted by code. `start` sees `.kickoff/` and offers to set up `project/` and a feature list from its documents. kickoff 0.9 stays installable from tag `v0.9.0`. | One-off reading is the AI's job. |
| 18 | **Version 1.0.0.** CHANGELOG "Breaking" section: the old → new mapping and how to switch. | Semantic versioning. |

### Table formats (ruling 6)

`<kick>/tasks.md`:

```markdown
## Tasks

| Task | Done when | After | Days (min–likely–max) | Confidence | Basis | Status |
| --- | --- | --- | --- | --- | --- | --- |
| shell: app shell, design rules in code, key screen | the key screen matches the chosen direction | | 2–3–5 | medium | similar shell last project | done |
| lend: lend flow on mock API | a librarian lends a book in 3 steps | shell | 2–3–6 | low | [unclear: barcode scanner] | doing |
| probe-scanner: can the old scanner talk to the browser? (probe) | answer recorded in design.md | | 0.5–1–2 | low | | todo |

## This is the product when

- the three main journeys can be completed …
```

- **Task:** a short key, a colon, then the plain title. `(probe)` in the title marks throw-away work.
- **After:** the keys this task waits for, comma-separated. An empty cell means the task can start at any time.
- **Days:** either `min–likely–max` (separators `-`, `–` or `/`) or one number, which counts as a point estimate.
- **Confidence:** low, medium or high.
- **Status:** todo, doing or done.

`project/roadmap.md`, same columns plus `Release` and `Kick`:

```markdown
## Features

| Feature | After | Days (min–likely–max) | Confidence | Basis | Release | Kick |
| --- | --- | --- | --- | --- | --- | --- |
| foundation: sign-in, database, deploy, one flow end to end | | 4–6–10 | medium | | first | foundation |
| lending: lend and return for real | foundation | 5–8–14 | low | | first | |
```

- **Kick:** the slug of the feature kick that implements the row, once that kick exists.
- **Progress:** comes from that kick (status `done`, or its remaining tasks).

`project/api.md`:

```markdown
## Endpoints

| Endpoint | Used by | Roles | Status | Cost |
| --- | --- | --- | --- | --- |
| GET /loans?member=&page= | lend, my-loans | librarian, member (own) | mock | |
| GET /reports/overdue | dashboard | librarian | mock | expensive: live aggregate over all loans |
```

**Status** is `mock` or `real`.

## 1. CLI (`cli/src/kick/`)

| Command | Does |
| --- | --- |
| `kick init --chat L --docs L --code L --ui L[,L] --commits L [--root R]` | Creates `docs/kick/project/` from the templates with `project.yaml`. Refuses when it exists, unless `--update` (then it only changes the languages). |
| `kick new <slug> --title T --kind product\|feature [--roadmap KEY]` | Creates `docs/kick/<slug>/` from the templates. It needs `project/` (it tells you to run `kick init`) and refuses a reserved or existing slug. `--roadmap` links the roadmap row. |
| `kick status [<slug>]` | With no slug, the product view: the languages line; every active kick with its kind, step, unclear count, tasks done/total and remaining estimate; the roadmap rows by state; the endpoints, mock versus real. With a slug: the detail, the unclear markers with their files, and the next step in words. |
| `kick estimate [<slug>] [--remaining] [--json]` | With a slug: the totals of that kick's tasks. With no slug: the product total from the roadmap, using each linked kick's remaining tasks instead of its row once the kick exists. Overhead from `project.yaml`, totals by release, the share of point estimates and low-confidence rows, and the time budget against the likely and max totals when a budget is set. |
| `kick check [<slug>]` | Checks the YAML files against the schemas and the three tables:<br>- ranges, unknown or cyclic `After` keys, duplicate keys, bad status values;<br>- a roadmap `Kick` that does not exist;<br>- an endpoint status other than mock or real.<br>Warnings for the advice cases of ruling 8. Exit 1 on errors only. |
| `kick done <slug>` | Sets `done` and moves the folder to `done/` (`git mv` when tracked). Warns when `result` is not agreed. |
| `kick companions [--step S] [--json]`, `kick companions mark <id> installed\|later\|never` | The catalogue with what each companion helps with, the account need, whether it is installed and the stored answer. `--step` lists only what that step calls for and is not yet installed or declined for good. |
| `kick doctor` | Checks the CLI version against the plugin, that ECC is present and recent enough, and gives a companions summary. |
| `kick setup` | Adds `docs/kick/**` to the GateGuard exemption in the project's `.claude/settings.json`. The skill asks before running it. |
| `kick hook session-start`, `kick hook post-write` | Session start prints the languages line and a two-line status when `docs/kick/` exists. Post-write runs `kick check` for an edited YAML file or a file with a checked table, and prints errors and warnings. Neither blocks. |

Modules:
- **Keep, trimmed and renamed:** `ecc.py` (detection and doctor), `estimate.py` (rows from the tables), `errors.py`, the hook module.
- **New:**
  - `projectfile.py` and `kickfile.py`: load the YAML files and derive the step.
  - `tables.py`: parses and checks the three tables.
  - `unclear.py`: finds the markers.
  - `companions.py`: the catalogue, detection and stored answers.
  - Schemas: `schemas/project.schema.json` (new) and `schemas/kick.schema.json`.
  - Templates: `templates/project/*` and `templates/kick/*`.
- **Delete:** `state.py`, `model.py`, `validate.py`, `schedule.py`, `calendar.py`, `workbook.py`, `lo_verify.py`, `export.py`, `docs.py`, `uxspec.py`, `labels.py`, `clarity.py`, `docker/`, the old schemas and templates, and their commands.
- **Hooks file:** SessionStart and PostToolUse only.

## 2. Skills

Every skill first reads `using-kick/references/plain-words.md` and `project/project.yaml` (languages). At its start it runs `kick companions --step <step>` and offers what is missing (ruling 14).

| Skill | Does |
| --- | --- |
| `using-kick` (router) and `/kick` | Startup: CLI version and `kick doctor`. Then `kick status` summarized in two plain lines, and the next step of the kick the person means, or a choice between kicks or "start one". Sends small work straight to ECC (ruling 12). |
| `start` | **Project set-up when `project/` is missing:**<br>- with code in the repo, reads it (`ecc:codebase-onboarding` or `ecc:code-explorer`) and drafts `overview.md`, `design.md`, `api.md` and `data.md` from what exists;<br>- proposes the languages and runs `kick init`;<br>- offers `kick setup`;<br>- offers to import a `.kickoff/` project.<br>**Then:** asks in words what is being kicked off ("a whole new product, or one feature or part of this app?") and runs `kick new`. When a roadmap exists, it offers the next row. |
| `understand` | One question at a time, then a play-back. Writes `brief.md`: problem, users, in / out, success, assumptions, what must not break (running project), a rough feature list (product kick), unclear markers. Agreement. |
| `shape` | **Product kick:**<br>- solution and architecture options that differ in kind (decision card, `ecc:architect`, `ecc:council` for close calls), with a diagram;<br>- technology, but not the data model;<br>- a screen map by journey with the first-release cut;<br>- UI direction: 2–3 directions, one key screen each;<br>- design rules;<br>- the UI languages;<br>- a technical risk list;<br>- a rough estimate for the whole product, and against `budget_days` a proposal of what to cut.<br>**Feature kick:** options only where there is a real choice; it reuses `project/design.md`, and the data and API for its part come here.<br>A fresh reviewer reads `design.md` before the agreement. |
| `plan` | Writes the task table. A product kick adds the probes and the "this is the product" criteria. Runs `kick estimate` and `kick check`, with an `ecc:planner` review for larger kicks. Agreement. |
| `build` | **Product kick:** the UI stage of ruling 9, then finishing per ruling 10.<br>**Feature kick:** ruling 11.<br>**Both:** set the task status in the table, write back changed decisions, and ask before going on when shape or plan is not agreed. Agreement on the result, then `kick done`.<br>References: `ui-on-mocks.md`, `trials.md` (tasks for real users, classifying comments), `feature-build.md`, `contract-tests.md`. |
| `change` | Something agreed changes: say in words what must follow (brief → design → tasks, and `project/` and the roadmap when shared), the extra days, and ask. Update in order, clear the affected agreements, log why. |

References in `using-kick/references/`:
- `plain-words.md`: the rule and a translation table for the new words.
- `methods.md`: interview, option decision, decision card, agreement, classifying feedback.
- `design-philosophy.md`: kept, cleaned of gate words.
- `ecc.md`: which ECC part each step uses, ECC's own approvals versus kick's agreements, GateGuard, the router.
- `companions.md`: how to offer and install, mirroring the catalogue.
- `practices.md`: the professional practices of brainstorm section 6 and where kick uses each.
- `lessons.md`: trimmed.

Each skill gets `tests/pressure.md` with three scenarios: a jargon scenario, "just start coding", and "let's design the database now" (product kick).

## 6. Risks

| Risk | Mitigation |
| --- | --- |
| A big rewrite loses behaviour people relied on | kickoff 0.9 stays installable from its tag. The CHANGELOG maps every removed command to its replacement or says "dropped". |
| Advice-only lets people build on a shape nobody agreed | Every skill asks before skipping an agreement and logs the answer; `kick status` shows "not agreed"; `kick check` warns. |
| The real UI on mocks still balloons with feedback | Comments classified with extra days, at most two rounds per screen, "this is the product" criteria set at plan time, and the remaining estimate at every showing. |
